# 3.6 Principles of Congestion Control

## The Problem

- **Congestion**: too many sources sending too fast for the network to handle
- Consequences: long queuing delays, packet loss (buffer overflow at routers)
- Packet retransmission treats the **symptom** (lost segment), not the **cause** (overloaded network)
- Costs of congestion:
  1. Large queuing delays
  2. Sender retransmissions consume bandwidth (wasted capacity)
  3. Unneeded retransmissions (premature timeout) waste router forwarding capacity
  4. Upstream bandwidth wasted on packets dropped downstream ("wasted work" problem)

## Notation

- `λ_in` = original data rate from application (bytes/sec)
- `λ'_in` = offered load = rate at which transport sends segments (original + retransmissions)
- `λ_out` = goodput = throughput at receiver

## 3.6.1 Causes and Costs of Congestion

### Scenario 1: Two Senders, Router with Infinite Buffers

- Two connections share router with output link capacity R
- No retransmission

**Result**:
- `λ_out` increases linearly up to R/2 per connection as `λ_in` → R/2
- Beyond R/2: throughput stays at R/2 but **delay → ∞**
- Cost: infinite queuing delay as load approaches capacity

### Scenario 2: Two Senders, Router with Finite Buffers, Retransmissions

Three sub-cases:

| Case | Description | Result |
|------|-------------|--------|
| a | Perfect knowledge: only send when buffer free | `λ_out = λ_in`, max R/2 |
| b | Retransmit only on confirmed loss | `λ_out < λ_in` (some bandwidth used for retransmits) |
| c | Premature timeouts: retransmit unnecessarily | `λ_out ≈ R/3` at `λ'_in = R/2` (1/3 wasted on duplicates) |

**Key cost**: `λ'_in > λ_in` — real bandwidth wasted on retransmissions

### Scenario 3: Four Senders, Finite Buffers, Multi-hop Paths

- A→C and D→B compete at router R1; B→D and A→C compete at R2
- At high offered load: B→D traffic floods R2, starving A→C traffic
- A→C throughput → 0 as load → ∞ (even though R1 forwarded A→C packets)
- **Ultimate cost**: upstream bandwidth entirely wasted — first-hop forwarding work is discarded at second hop

## 3.6.2 Approaches to Congestion Control

### End-to-End Congestion Control

- Network layer provides **no explicit feedback**
- End systems infer congestion from observed behavior (loss, delay)
- TCP uses this approach: packet loss (timeout or 3 dup ACKs) = congestion signal
- TCP Vegas: uses increased RTT as congestion signal

### Network-Assisted Congestion Control

- Routers provide **explicit feedback** to senders
- Two forms:
  1. **Single bit**: router marks packet to indicate congestion (e.g., ATM ABR, ECN in IP)
  2. **Explicit rate**: router tells sender maximum rate it can support

**Feedback path variants** (Figure 3.49):
- Router → directly informs sender
- Router marks receiver-bound packet → receiver notifies sender in next ACK

**Examples**:
- ATM Available Bit Rate (ABR) — explicit rate feedback
- ECN (RFC 3168) — 2 bits in IP header (covered in §3.7.2)
- DCQCN — data center networks

### Comparison

| Approach | Network involvement | Reaction time | Examples |
|----------|--------------------|--------------:|---------|
| End-to-end | None | Slower (RTT-based) | Classic TCP (Reno, Tahoe, CUBIC) |
| Network-assisted | Router marks/rates | Faster (proactive) | ECN, ATM ABR, DCQCN |
