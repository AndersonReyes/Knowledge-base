# 3.3 Connectionless Transport: UDP

## Overview

- Defined in **RFC 768**
- Does just about as little as a transport protocol can do
- Adds multiplexing/demultiplexing + light error checking to IP
- Application talks almost directly with IP

## Why Use UDP?

| Reason | Details |
|--------|---------|
| No connection establishment | No handshake delay; DNS benefits hugely |
| No connection state | Can support more active clients than TCP |
| Small header overhead | 8 bytes vs. 20 bytes TCP |
| No congestion control | Can blast at any rate; good for multimedia, real-time |
| Application-controlled send rate | No throttling |

**QUIC** (Quick UDP Internet Connections, used in Chrome/HTTP/3): built reliability/CC on top of UDP at application layer to avoid TCP overhead.

## Popular Applications and Their Protocols

| Application | App-Layer Protocol | Transport |
|-------------|-------------------|-----------|
| Email | SMTP | TCP |
| Remote terminal | Telnet | TCP |
| Secure remote terminal | SSH | TCP |
| Web | HTTP / HTTP/3 | TCP (HTTP), UDP (HTTP/3) |

**Note**: Multimedia over TCP is increasingly common as some organizations block UDP for security.

## 3.3.1 UDP Segment Structure

```
 0                   16                  31
 +--------------------+--------------------+
 |    Source Port     |  Destination Port  |  2 bytes each
 +--------------------+--------------------+
 |       Length       |      Checksum      |  2 bytes each
 +--------------------+--------------------+
 |                                         |
 |              Application Data           |
 |                                         |
 +-----------------------------------------+
```

- **Source Port**: 16 bits — used as return address
- **Destination Port**: 16 bits — demultiplexing
- **Length**: length in bytes of UDP segment (header + data); minimum = 8
- **Checksum**: error detection
- **Data field**: application data (DNS query/response, audio samples, etc.)

Header total: **8 bytes** (vs. TCP's 20 bytes)

## 3.3.2 UDP Checksum

### Purpose
End-to-end error detection even though some link-layer protocols (e.g., Ethernet) already do this.  
Reason: not all links provide error checking; errors can occur in router memory during packet processing.

### Computation (Sender)
1. Treat segment (header + data + pseudo-header) as sequence of 16-bit words
2. Compute 1's complement sum of all 16-bit words
3. Overflow bits are **wrapped around** (end-around carry)
4. Take 1's complement of the sum → this is the checksum

### Example
```
Word 1:  0110011001100000
Word 2:  0101010101010101
Sum:     1011101110110101

Add W3:  1000111100001100
         ----------------
         0100101011000010  (overflow wrapped)

1's comp: 1011010100111101  ← checksum stored in segment
```

### Verification (Receiver)
- Sum all four 16-bit words including checksum
- Result should be `1111111111111111` (all 1s)
- Any 0 bit → error detected

### Limitations
- Detects errors but **does not correct** them
- Some implementations discard damaged segments; others pass with warning
- Cannot detect all errors (e.g., two complementary bit flips sum to same value)

## UDP vs TCP Summary

| Feature | UDP | TCP |
|---------|-----|-----|
| Connection | Connectionless | Connection-oriented |
| Reliability | No | Yes |
| Ordering | No | Yes |
| Flow control | No | Yes |
| Congestion control | No | Yes |
| Header size | 8 bytes | 20 bytes |
| Speed | Faster | Slower |
| Use case | DNS, streaming, gaming | HTTP, FTP, email |
