# 4.5 Middleboxes

## Definition (RFC 3234)

> "Any intermediary box performing functions apart from normal, standard functions of an IP router on the data path between a source host and destination host."

Encountered throughout the text: web caches (§2.2.5), TCP connection splitters (§3.7), NAT (§4.3.4), firewalls, IDS, load balancers (§4.4).

## Three Service Categories

### 1. NAT Translation
- Rewrite datagram header IP addresses and port numbers
- Implement private network addressing
- See §4.3.3

### 2. Security Services
- **Firewalls**: block traffic based on header-field values; redirect for additional processing
  - Can perform **deep packet inspection (DPI)** — inspect beyond headers into payload
- **IDS (Intrusion Detection Systems)**: detect predetermined attack patterns, filter packets
- **Application-level filters**: block spam/phishing email based on IP addresses and message content

### 3. Performance Enhancement
- Compression
- Content caching
- **Load balancing**: distribute HTTP requests, search queries across server pool

## NFV: Network Function Virtualization

**Problem**: dedicated hardware middleboxes → high operational and capital costs (separate hardware, separate software stacks, separate management skills).

**NFV approach**: commodity hardware (servers, switches, storage) + specialized software on a common software stack — mirrors SDN's approach applied a decade later.

**Alternative**: outsource middlebox functionality to the cloud.

## Architectural Tension

### The Old Separation
- Network core: dumb IP routers, only process IP datagram headers
- Network edge (hosts): all application/transport logic
- Clear layer separation

### Middlebox Violations
- NAT box: rewrites **network-layer** IP addresses AND **transport-layer** port numbers
- In-network firewall: inspects **application-layer**, transport-layer, and network-layer headers
- Email security gateways: inspect and filter **application-layer** email content

### The Debate

**Against middleboxes** ("architectural abomination" [Garfinkel 2003]):
- Violate end-to-end principle
- Break NAT traversal for P2P apps
- Complicate network management

**For middleboxes** [Walfish 2004]:
- "Exist for important and permanent reasons"
- Fill real needs that pure end-to-end architecture cannot (NAT, firewalls)
- More middleboxes in the future, not fewer

## Internet Architecture Principles

### RFC 1958: Architectural Principles of the Internet
Three core tenets:
1. **Goal**: connectivity
2. **Tool**: the Internet Protocol (IP) — one universal network-layer protocol
3. **Intelligence**: end to end, not hidden in the network

### The IP Hourglass / Narrow Waist

```
Application layer  (many protocols: HTTP, SMTP, DNS, ...)
Transport layer    (TCP, UDP, QUIC, ...)
─────────────────────────────────────────
     Network layer  ← ONE PROTOCOL: IP
─────────────────────────────────────────
Link layer         (Ethernet, WiFi, cellular, optical, ...)
Physical layer     (many technologies)
```

- IP is the "narrow waist" — the only universal requirement for Internet connectivity
- Hides link-layer technology diversity from applications
- "Spanning layer" [Clark 1997]: translates all lower-layer technologies into one common service
- Enabled phenomenal growth: any link technology can connect to Internet by implementing IP
- **Observation**: middleboxes are widening the narrow waist (NAT, firewalls add to required infrastructure)

### The End-to-End Argument (Saltzer 1984)

Core idea:
> "The function in question can completely and correctly be implemented only with the knowledge and help of the application standing at the end points of the communication system. Therefore, providing that questioned function as a feature of the communication system itself is not possible."

**Example — reliable data transfer**:
- Routers can crash, holding queued packets → packets lost even without buffer overflow
- Link-layer local error control alone is incomplete
- Therefore: reliable transfer must be implemented **end-to-end** (TCP), not just in the network
- Network can provide local error control as a **performance enhancement**, but not as a substitute

**Contrast with telephone network**:
- 20th century telephone: dumb endpoints + smart switches
- Internet: **smart endpoints** (programmable computers) + dumb core routers

**Tension with middleboxes**: middleboxes break the end-to-end principle by placing functionality (NAT, firewall, DPI) inside the network.

RFC 1958 canonical references:
- [Saltzer 1984] — the end-to-end argument
- [Clark 1988] — design philosophy of DARPA Internet Protocols

### Lesson from IPv6 Deployment

- Network-layer protocol changes are **extremely slow** (IPv6 development started ~1990s, still not universal)
- Application-layer protocol changes are **fast** (Web, streaming, IM, social media deployed in years)
- Analogy: changing network-layer = replacing house foundation; changing app-layer = repainting house
