# 6.2 Error-Detection and -Correction Techniques

## Setup

```
Sender:  [   D   | EDC ]  ──link──▶  Receiver: [ D' | EDC' ]
         d bits  r bits                         (may have flipped bits)
```

- **D**: data to protect (includes datagram + link frame header fields)
- **EDC**: Error Detection and Correction bits appended to D
- Receiver asks: "Is D' == D?" given only D' and EDC'
- Even with EDC, **undetected errors are possible** — larger EDC overhead → lower undetected-error probability

## 6.2.1 Parity Checks

### Single-Bit Parity

- Sender chooses 1 extra bit so total 1s in (d+1) bits is even (even parity) or odd (odd parity)
- Receiver counts 1s: odd count with even parity scheme → error detected
- **Detects** single-bit errors (and any odd number of errors)
- **Miss rate**: burst errors approach 50% undetected — inadequate for practice

### Two-Dimensional Parity

```
         col parity
         ↓ ↓ ↓ ↓
row 1: [ 1 0 1 1 ] → row parity bit
row 2: [ 0 1 1 1 ] → row parity bit
row 3: [ 1 1 0 1 ] → row parity bit (error at (2,2) detectable + correctable)
       ──────────
       col parity bits  +  overall parity bit
```

- d bits arranged in i rows × j columns
- Parity computed per-row and per-column → i+j+1 parity bits total
- **Single-bit error**: both the row parity and column parity for that position fail → identifies exact bit → **correctable**
- **Two-bit errors**: detectable but **not** correctable
- **Forward Error Correction (FEC)**: ability to detect AND correct at receiver — used in audio CDs, reduces retransmissions, important for real-time / high-latency links

## 6.2.2 Checksumming Methods

- d bits treated as sequence of k-bit integers, summed → use sum as EDC
- **Internet checksum**: bytes treated as 16-bit integers; 1s complement sum → carried in header
  - TCP/UDP: covers header + data
  - IP: covers IP header only (transport layer has its own checksum)
- Simple and fast → implemented in **software** at transport layer
- Weaker error protection than CRC
- Tradeoff: checksum in software (transport) vs. CRC in hardware (link)

## 6.2.3 Cyclic Redundancy Check (CRC)

Also called **polynomial codes** — widely used at the link layer, implemented in hardware.

### Mechanics

Given:
- `D`: d-bit data
- `G`: (r+1)-bit generator (leftmost bit must be 1), agreed upon by sender/receiver
- Goal: sender appends r bits `R` to D so that `(D·2^r XOR R)` is exactly divisible by G (mod-2 arithmetic)

**Computing R:**

```
R = remainder[ D·2^r / G ]   (mod-2 division)
```

**Transmitted**: `D·2^r XOR R`  — total d+r bits

**Receiver check**: divide received (d+r) bits by G; nonzero remainder → error detected

### Mod-2 Arithmetic Rules

- Addition = Subtraction = XOR (no carries/borrows)
- `1011 XOR 0101 = 1110`
- `1001 XOR 1101 = 0100`
- Multiplication/division same as binary except addition uses XOR

### Example

```
D = 101110  (d=6)
G = 1001    (r=3)
R = remainder(101110·2³ / 1001) = 011
Transmitted: 101110 011
```

### Standard CRC Generators

| Standard | Generator (hex/binary) | Notes |
|----------|----------------------|-------|
| CRC-8 | 8-bit G | simple |
| CRC-12 | 12-bit G | |
| CRC-16 | 16-bit G | |
| CRC-32 | `100000100110000010001110110110111` | adopted by many IEEE link-layer protocols |

### CRC Error Detection Properties

- Detects all **burst errors ≤ r bits** (r = degree of G)
- Burst of length > r+1 detected with probability **1 − 0.5^r**
- Detects **any odd number of bit errors**
- Very strong protection for the r-bit overhead cost
